# Editable delivery and review (Transovo master 8dac307e + 24de16dd/cc092ad, Nov 18 2026)

Apply alongside the installed production routine, including revisions, clip jobs and brand kits. Paths below are this box's install (`K=/workspace/ms_producer_editable`).

- **Live delivery, render first (Rick, Nov 19; reverses the Nov 18 "no automatic MP4" rule).** When `job.delivery.mode` is `"live"`, follow **"Live delivery"** below. After approval the master is rendered once and made playable right away with `approveMaster` while the job stays open. **Since Nov 19 that render runs on Modal CPU (see "Modal render" below), not on this box; the box path is the fallback.** The editable live package then uploads in the background (`/workspace/motion_kit/bg_delivery/`), and the job completes with `delivery:"live"` only after every editable file is confirmed ready. Captions are always a separate editable track, never burned in. Jobs without `delivery.mode:"live"` keep the render-once publish path.
- **Progress on real transitions only.** Stages: research, story, voice, design, scenes, review, fixing, rendering, delivering (a live job goes review → rendering → delivering; the background script posts the delivering counts). Report the scene number while building and completed/total files while uploading (publish-editable.mjs does the upload counts itself).
- **Review.** No rendering until everything is approved (Rick, Nov 18). Review in the browser with still screenshots (`stillBrowser` or the engine's still command) at 480p by default, full size only for a frame that can't be judged at 480p (SKILL.md section 7): first, busiest and last frame of each scene, plus wherever something changes. After a correction, capture only the affected scene and its boundary frames. For movement or sync, step stills through the section or play it live in the browser; never encode a clip to review. Browser engines are always reviewed with browser stills. The non-browser engines (Cinematic Skill, Manim, Natron, any existing Node Skia script) are checked with the exact still recipes in `film-pipeline.md`; before approval nothing beyond the exact frame or few seconds being checked is rendered. Final full watch: on every job (live or not), render the master once after approval and watch it before delivery.
- **Frame packs.** `$K/producer/lib/bundle.mjs` + `frame-packs.mjs` (installed together) pack numbered PNG/JPEG/WebP frames losslessly into `*.frames` sources (≤16 MB each) when bundles are built. The deterministic runner and sim read packs. A 10 s, 5-scene film is about 41 editable assets instead of 336.
- **Render-once publish path (only jobs WITHOUT `delivery.mode:"live"`)** (replaces live `publish-portable.mjs` uploads):
  1. Build as in SKILL.md section 8 (`build-editable-project.mjs`), then QA.
  2. Validate: `node $K/producer/bin/publish-portable.mjs --dir …/editable/out --dry-run` must PASS (no network). Never run publish-portable.mjs live any more.
  3. Stage the approved package on durable storage: `MOTION_STUDIO_JOB_DIR=/workspace/motion_durable/<jobId> node $K/producer/bin/stage-approved.mjs --dir …/editable/out --project-id <projectId> --editor-base /workspace/motion_jobs/<jobId>/editable/editor-base.mp4` (writes `approved/{package.json,bundles.json,blobs/}` via a staging dir + rename).
  4. Publish with the job URL and job token in the environment (from `secrets/`, never on the command line or in chat): `MOTION_STUDIO_JOB_URL=… MOTION_STUDIO_JOB_TOKEN=… node $K/producer/bin/publish-editable.mjs /workspace/motion_durable/<jobId>/approved /workspace/motion_durable/<jobId>/approved/bundles.json --complete`. It uploads the master first and marks it Video ready, then 8 files at a time with retries, reuses committed receipts, publishes the portable version only after every asset is ready, then completes with the master's measured duration. It pings the job checkpoint every 60 s while it runs (a script HTTP call, no agent turns).
  5. If interrupted (restart, 5xx), re-run step 4 unchanged; it resumes from receipts. Don't rebuild or re-render. For recovery from an earlier job on the same project set `MOTION_STUDIO_RECOVERY_SOURCE_JOB=<old jobId>`.
- **Lease.** The creative lease stays 30 min (server env `MOTION_STUDIO_CREATIVE_LEASE_MS=1800000`) and every job-token call renews it. Do not schedule agent-level heartbeats; normal progress posts at stage changes are enough.
- **Keep** the approved folder until the portable publication is acknowledged. Reuse the reviewed master when completing. Group the editable timeline like song tracks (Rick, Nov 18): all text, titles and captions on one track; Main Voice on one; Ad-libs on their own; Main Visuals on one; other audio on one. Never a separate piece per line of text. Keep original item IDs and timings. This keeps the file count small; uploads still go 8 at a time (publish-editable.mjs), and every file must be confirmed as committed.

## Live delivery (`job.delivery.mode:"live"`; Rick, Nov 18; contract in `delivery-contract.md` §0)

The agent's job ends at an approved master the customer can play at once, plus a live-playable, editable project that a background script publishes. Nothing about how scenes are designed or reviewed changes; only the packaging changes.

1. **Build and review exactly as before** (SKILL.md sections 4–7): browser stills at exact times, non-browser engines with their still recipes, no encode before approval, no cap on fix rounds. Footage stays inside the browser scene as `video` layers. Every title and graphic keeps its `startMs`/`endMs` active window. A non-browser engine's approved picture (Cinematic Skill, Manim, Natron, a Node Skia script) comes in as a plate: render ONLY that plate once after its stills are approved, as prepared media for a `video` layer, never a scene clip of the whole composite. The film master is rendered only after approval (step 4).
2. **Write the live spec.** `editable/project.json` (the same spec as before: `title`, `format`, `theme`, `fonts`, `audio.file` = the approved mix, `scenes[]` of `transovo.layer-scene/1`) plus `live`: `{stems:{main_voice:[{file,label}], adlibs:[…], other_audio:[{file:music},{file:sfx},{file:footage_audio}]}, captions:"<captions.json | .vtt | .srt>"}`. Stems are the full-length 48 kHz WAVs from the sound step (`film-pipeline.md` §6), grouped like song tracks (Rick): Main Voice, Ad-libs, Main Visuals, Text, Other audio. Captions are word-timed cues, never burned in.
3. **Dry run (no network):** `node /workspace/ms_producer_editable/producer/bin/publish-live.mjs --spec /workspace/motion_jobs/<jobId>/editable/project.json --out /workspace/motion_jobs/<jobId>/editable/live --job-dir /workspace/motion_jobs/<jobId> --dry-run`. It builds bundles, stems, the caption file, the export recipe, the producer document and the `transovo.live-project/1` timeline, renders NOTHING, and runs Transovo's own validators locally. It must print `PASS`. The one expected warning is "EXPORT GAP (server)" (Transovo's Export can't yet read a document without a master; that is ChatGPT's fix, not ours).
4. **Final check.** On Modal (default) the final check is Modal's automatic QA of its own output: frame count, duration, audio present, black gaps, loudness. Nothing is rendered or watched locally. Only in the box fallback: render the master once (SKILL.md section 8 render rules) to `<J>/deliver/master.mp4` and do the section 7 final check on it; loudness and true peak are checked on the master's mix.
5. **Deliver (box fallback only; the default is "Modal render" below):** `bash /workspace/motion_kit/bg_delivery/launch.sh <J> <J>/deliver/master.mp4`.
   - Foreground, a few seconds: it uploads `master.mp4` (`kind:"video"`), sends `assets {action:"approveMaster"}` (the customer can play it now) and posts progress. It never calls `/complete`.
   - Then `repack-live.mjs` packs every scene-bundle file into ≤6 MB `.frames` packs (byte-identical, validated). This means fewer uploads, and scene-host keeps each pack in its 8 MB cache.
   - Detached (`setsid nohup`, survives the turn): `watchdog.sh` → `deliver-editable.mjs` uploads 8 at a time. Each file is retried with backoff for up to 8 h. It resumes from `deliver_bg/state.json` plus server receipts, pings `/checkpoint` every 60 s to hold the lease, and posts "Preparing the editable version: n / total". It confirms every file `ready` with a matching sha256, validates locally, publishes ONE portable version, checks it carries this live timeline, then calls `/complete {delivery:"live", portableVersionId, durationMs}`.
   - Result: `deliver_bg/DONE`, or `deliver_bg/FAILED` with a reason, plus `status.json` and a progress note.
   - Do not run `stage-approved.mjs`, `publish-editable.mjs` or `publish-portable.mjs` on a live job, and never run `publish-live.mjs` without `--dry-run` while a background delivery exists: the server keeps the first version a job publishes.
6. **If interrupted** (restart, crash, kill), run `bash /workspace/motion_kit/bg_delivery/resume-all.sh`. It is safe to run at any time. The box has no cron or systemd, so the routine runs it at the start of every run. Committed files are never uploaded twice.
7. **Rick's test jobs:** send Rick the job id and a 480p (or lower) copy of the master.

## Clean picture and timed overlays (24de16dd)

- **Two videos.** The reviewed composite (`out/master.mp4`, text and graphics burned in) stays the master for playback and download. Also make the **clean cut** `editor-base.mp4`: the same edit with only the plates/footage (no editable titles, graphics or captions), same length, fps and size, H.264 yuv420p, no audio (audio is its own timeline item). Example for plate scenes: trim each `plate_S<n>.mp4` to its scene duration and concat with ffmpeg. Pass it to stage-approved.mjs with `--editor-base`; the server shows it on the editor canvas and keeps the master for playback.
- **Timed overlays.** Every editable title, graphic and audio item gets its active window in the layer scene: `startMs`/`endMs` (scene-local ms) on the layer in `editable/project.json`, plus keyframes inside that window. Do not make a layer span the whole scene just to hide it with opacity. The gap before/after needs no media. For transitions the user should be able to change, keep both source clips with handles and the cut timing; otherwise bake them into the plate.
- **No render captures in delivery.** Final renders stream frames into the encoder. Keep review stills **outside** the scene folder (e.g. `/workspace/motion_jobs/<jobId>/qa/`); for stills during encoding pass a framesDir outside the scene plus explicit `reviewFrameIndices`, or seek with `stillBrowser`. The bundle builder skips `frames/`, `screenshots/`, `render-cache/` folders and `f_*/frame_*/screenshot_*` stills; publish-editable.mjs refuses a package that still has them. Genuine image-sequence artwork must be declared in buildBundle `sourceFiles`.
- **Video plates.** build-editable-project.mjs still pre-decodes each video layer to a JPEG sequence inside the scene (`media/<plate>_<layer>_frames/00001.jpg…`). These are genuine scene inputs (packed losslessly, ~1 pack per scene) and are allowed.
- **Check before the final render:** move one title's startMs and take browser stills before, during and after the new window; the title must appear only inside it.

## Modal render (default for live jobs; Rick, Nov 19)

Scripts: `/workspace/motion_kit/modal/` (`README.md`). The bot's job ends at "render submitted".
1. **Prepare the editable package** as in steps 2-3 above, then `repack-live.mjs --live-dir <J>/editable/live`.
2. **Compose the film** into `<J>/film/`: `index.html` (the whole film), everything it loads (fonts, footage as JPEG sequences or frame packs, images), `audio.wav` (final mix, exactly the film's length, about -14 LUFS) and `film.json` `{title,width,height,fps,frameCount}`.
   - The page exposes `window.__scene = {fps, duration, frameCount, seek}` and `window.__ready = true`, both assigned only after fonts, data, images and a first seek are done.
   - `await __scene.seek(tSeconds)` is deterministic: state comes only from `t` (no wall clock, no unseeded random; grain keyed by frame index). The viewport is exactly the film's size. No external requests (blocked on Modal); no `<video>` elements (untested there); no burned-in captions; no audio in the page.
   - It must match the approved stills: seek the same times and compare before packing.
3. **Pack:** `python3 /workspace/motion_kit/modal/make_bundle.py --job-dir <J> --check-page`. It writes `<J>/deliver_modal/render_bundle_v1.zip` (`project.json` at the root with `composition.entryFile`, `mixedAudioFile`, fps, size, `frameCount`, `durationMs`, sha256 list; no symlinks; at most 10,000 files) plus the editable package Modal publishes: `package.json` (`transovo.motion-package/1`), `bundles.json`, `live-project.json`, `blobs/<sha256>`. A changed bundle after a submit needs a new file name (`render_bundle_v2.zip`).
4. **Submit once:** `bash /workspace/motion_kit/modal/submit.sh <J> cpu`. Segment size is chosen from the length (150-450 frames, at most ~96 containers); the cost estimate stays under the $5 job cap; exit 4 means the Modal publish fix is not confirmed deployed, so use the fallback and tell Rick.
5. **Stop.** No local render, no polling, no watch-through. Modal renders the segments in parallel, joins, runs QA, uploads `master_cpu.mp4` and `share_cpu.mp4`, approves the master, publishes the editable version and completes with `delivery:"live"`. One `status.sh` for the final chat message is enough.
6. **Failure:** `qa_fail` or a failed Modal call: report the redacted reason, never resubmit to the same job without Rick. A submit that fails twice (not a QA failure) switches to the box fallback above.
